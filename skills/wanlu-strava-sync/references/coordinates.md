# 坐标自动诊断与纠偏

## 先区分编码和坐标系

FIT 标准位置字段是有符号 32 位 `semicircles`，度数 = 整数 × 180 / 2^31。不是十进制度数，也不是经纬度颠倒。脚本按消息定义、大小端、标准字段类型读取，不能看到很大的整数就直接当度数。无效哨兵不参与转换，格式不明时停止猜测。

WGS-84 / GCJ-02 / BD-09 是另一层问题：同一个物理地点的数字不同。FIT 容器和经纬度范围通常没有足够信息证明属于哪一种。GPS 或 FIT 来源不等于其一定是 WGS-84，顽鹿来源也不等于一定经过 GCJ-02 偏移。

## AI 如何判别

每条骑行分别检查，不把上一次的结论无条件套到整个账号。

1. 运行 `fit_coordinates.py analyze`。输出 CRC、SHA-256、有效轨迹点数、范围、最多 9 个沿程样本。`asWgs84` 是原始数值直接解释为 WGS-84，`ifGcj02` 是假设原始为 GCJ-02 的近似逆转换候选；候选不是自动识别结论。`conversionEligible` 仅表示数值在算法边界内，不证明位于大陆或属于 GCJ-02。
2. 优先使用这条 FIT 对应的明确导出说明、带坐标系声明的数据或可靠设备配置。APP 截图使用高德底图，仅能说明渲染时使用某坐标系，不能证明原始 FIT 被改写。
3. 缺少明确来源时，用已知坐标系的参照检查沿程分散的位置和明显转弯、桥梁等。至少三个分散且可对应的地标都支持同一候选，另一候选存在方向一致的显著偏移，才作有证据的推断。仅一处“更贴路”、两种候选各有好坏、GPS 漂移、平行道路或山地小路不足以确定。
4. 所有比较统一坐标系。不能直接把原始 WGS-84 数字放到 GCJ-02 底图再宣布偏移；不能用 GCJ-02 地图拾取坐标冒充 WGS-84 真值。使用截图时需要可辨识比例尺、位置参照和已知底图转换规则；单看缩略图不能定论。现有权限内可查地图，但不要把整条私人轨迹上传到公共轨迹分析服务。
5. 结论只用「确认 / 有充分证据推断 WGS-84」「确认 / 有充分证据推断 GCJ-02」「无法确定」「无 GPS」。写出实际依据和其限制，不编造概率、匹配分数或未看到的地图证据。

无法确定时默认保留原始 FIT，并在结果标明未转换；不要用一次真实 Strava 上传试错再删除重传来识别坐标系。用户要求必须纠偏时，先请求缺少的参照。如果疑似 BD-09、其他坐标系、混合坐标或经纬度顺序异常，当前工具不自动修复，说明不支持。

## 确认后自动转换

仅当证据支持 GCJ-02，且 AI 确认整条轨迹适用中国大陆转换时执行：

```sh
python3 <skill-directory>/scripts/fit_coordinates.py convert /ABS/PATH/original.fit --output /ABS/PATH/ride.wgs84.fit --source-crs gcj02 --mainland-confirmed --evidence '记录本次实际参照和判断依据'
```

`--mainland-confirmed` 是执行者的明确判断，不是脚本能识别行政边界。算法矩形范围包含部分不适用地区；港澳台、跨境、边界附近或混合数据不自动整段转换。逆转换是近似算法，不是官方高德反向转换接口，也不承诺测绘精度。

脚本只改标准 record 经纬度、session 起点 / 边界、lap 起终点 / 边界；未知字段和开发者字段逐字节保留，不改变时间、功率、心率、踏频、距离、海拔或消息布局。若其他未知字段嵌有位置数据，不会识别或重写。14 字节头部 CRC 和文件 CRC 重新计算，写入新文件，原文件不覆盖。

输出旁边的 `.coordinates.json` 保存来源 / 输出 SHA-256、转换方向、算法和依据。匹配审计记录的 WGS-84 副本会拒绝再次纠偏；外部文件缺少此记录时仍需要判断，文件名不是坐标系证明。审计和 FIT 都以 0600 创建，包含敏感位置信息，不打包发布。

上传实际选定副本，在 `receipt --uploaded-file …` 中记录它：副本与原始哈希不同时，必须有匹配的转换审计记录。保存活动后检查地图，若仍有异常先报告，不自动删除或改写已创建活动。
